# SDD Spec

입력은 사용자가 첨부하거나 경로로 지정한 파일만 사용한다. 입력 파일을 받지 않았으면 파일 탐색·명세 작성·갱신·추가 입력 요청 없이 종료한다.

입력 파일이 제공되면 [spec.template.md](spec.template.md)를 읽고 채운다. 사용자 지정 경로·기존 명세를 우선하고, 기본 출력은 `spec.md`다.

한국어 문어체로 작성하고 확정·위임·미정을 구분하며, 실행한 검증만 통과로 표시한다.

도메인 전문 지식이 없는 독자도 명세만 읽고 각 Feature의 통과·실패를 판정할 수 있도록 쉬운 표현과 필요한 설명을 쓴다.

## 작성 순서

1. 지정된 원문·실제 데이터·담당자 답변과 기존 구현·검증 기록을 확인한다. 자료로 확인되지 않은 정보는 해당 Feature에 미확인으로 표시하고, 필요한 입력·경로는 사용자에게 요청한다.
2. 개요·용어·핵심 요구사항·Feature 제목·질의 목록을 먼저 저장한 뒤 통과 조건을 채운다. 데이터는 구조·표본부터 확인하고 기존 명세 갱신에 필요한 관련 코드·검증 기록만 읽는다. 최초 명세 생성 시 사용자가 지시나 제공 자료로 전달한 개발 시간이 있으면 그 값을, 없으면 180분을 기준으로 Feature의 범위와 구현 수준을 정의한다. 개발 시간은 이 판단에만 사용하고 명세·응답에 시간 표기·시간 배분·초과 위험·완료 보장에 관한 설명을 넣지 않는다. 기존 명세 갱신 시 개발 시간을 다시 묻거나 재산정하지 않는다.
3. **개요·용어·핵심 요구사항:** 개요 세 줄을 쓰고, Feature·통과 조건에서 뜻을 오해하면 요구사항이나 통과·실패 판단이 달라지는 업무 개념만 용어 표에 한 문장씩 정의한다. 일반 용어·약어와 개요나 관련 기능에서 충분히 설명한 표현은 제외하고, 데이터 열 이름·형식·값 규칙은 데이터 계약에서 설명한다. 한 개념은 같은 용어로 부르며 본문과 용어 표에 정의를 중복하지 않는다. 정의할 용어가 없으면 표 대신 `없음` 한 줄만 남긴다. 원문에 없는 사용자 역할·정의는 미정 또는 가정으로 표시하고 결과·범위·통과 조건에 영향을 주면 Q번호로 연결한다. 핵심 요구사항은 원문의 필수 항목을 3~7줄로 묶고 각 줄 끝에 원문 위치를 붙인다. 필수 항목이 많으면 관련 항목을 한 줄에 묶어 모두 보존한다.
4. **Feature 목록:** 아래 분할 기준에 따라 한 번에 구현·검증·검토할 수 있는 기능을 F01부터 나눈다. 각 항목은 요구와 통과 조건 1~3개를 적고, 미정·가정은 있을 때만 질의 번호로 연결한다. 요구는 주체(사용자·시스템)·행동·결과·원문 근거로 적는다. 통과 조건은 실제 값을 넣은 입력 → 기대 결과로 적으며 오류·조건 변경·재시작 등 원문 조건을 포함한다. 서로 다른 큰 기능을 한 통과 조건에 나열해 개수를 맞추지 않는다. 여러 기능에 걸친 필수 조건은 공통 완료·제출 조건으로 연결한다.
5. 기존 Feature ID·합의·진행 근거를 유지한다. 상태는 `미착수·완료·보류`다. 완료는 구현 완료를 뜻하며, 실제 구현과 수행 가능한 필수 검증의 통과 근거가 있어야 한다. 사람의 UI 확인만 남으면 완료로 두되 검증 결과에 `사람 확인 대기`를 별도 기록한다. 의존 결정으로 멈추면 보류, 나머지는 미착수에 진행 근거를 남긴다.
6. **담당자 질의:** 아래 작성·답변 반영 기준에 따라 결과·범위·통과 조건을 바꾸는 미정 사항을 Q번호로 연결한다. 우선순위대로 한 번에 최대 5개의 결정을 실제로 질문하되 질문이 적으면 그 수만 묻는다. 나머지 미정은 해당 Feature에 남긴다. 답변이나 해당 결정의 명시적 위임 전에는 실제로 그 결정에 의존하는 범위만 보류하고 독립 작업은 진행한다.
7. **메모:** 입력에 데이터 파일이 있으면 키·단위·누락 처리 계약 한 줄, 계산 로직이 있으면 방식·이유·한계 한 줄, 모듈이 셋 이상이면 모듈별 책임을 한 줄로 적는다. 조건에 해당하는 항목만 남긴다.
8. 원문의 필수 항목이 Feature와 통과 조건 또는 공통 완료·제출 조건에 모두 반영됐는지, 설명 부족으로 요구사항이나 통과·실패 판단이 달라질 표현이 남아 있는지 확인하고 저장한다. 필요한 설명은 용어 표·관련 기능·데이터 계약 중 적절한 한 곳에 두며, 등장하는 용어·약어를 빠짐없이 용어 표에 등록하려 하지 않는다. 구현까지 요청받았다면 확정·위임된 범위에서 다음 단계로 이어간다.

## Feature 분할

- Feature는 하나의 주요 목적과 확인 가능한 결과를 가진 구현 단위로 나눈다. 한 항목의 관련 코드·처리 규칙·검증 근거를 한 번에 이해하고 검토할 수 있는 크기를 기준으로 삼으며, 개수를 최소화하거나 고정 개수를 채우는 것을 목표로 삼지 않는다.
- 같은 업무 흐름 안에서도 각각 구현·검증·수정할 수 있는 큰 기능은 분리한다. 예를 들어 데이터 입력·수정, 핵심 계산, 결과 화면은 구분할 수 있다. 핵심 계산도 입력·출력과 통과 조건을 따로 확인할 수 있으면 별도 Feature로 둔다. 한 항목에 여러 화면과 큰 처리 규칙이 몰리거나 수정 영향·검토 범위를 설명하기 어려우면 다시 나눈다.
- 같은 방식으로 처리하는 파일 종류·필드·사소한 CRUD 차이, 함수·기술 계층마다 Feature를 늘리지 않는다. 관련 코드와 규칙을 함께 검토할 수 있는 작은 동작은 묶고, 요구사항의 전체 흐름은 Feature 간 연결로 보존한다.
- 오류 처리·입력 검증·버전 관계·저장 등은 관련 기능의 통과 조건에 포함하거나 공통 조건으로 연결한다. 독립적인 입력·출력과 검증 목적이 없는 보조 처리를 각각 별도 Feature로 늘리지 않는다.
- Docker 빌드·실행, 필수 검증, 제출 문서·대화·장애 기록은 원문에서 요구한 경우 `공통 완료·제출 조건`으로 분리한다. 각 조건에도 입력/절차 → 기대 결과와 원문 근거를 적으며 전체 완료 판정에 포함한다.
- 사용자 지시나 원문에 없는 기능·복잡한 최적화·운영 체계를 추가하지 않는다. 원문 필수 기능을 임의 삭제하거나 선택 사항으로 바꾸지 않는다. 어려운 부분은 요구를 만족하는 단순한 구현 방법과 한계를 기록하고, 정말 범위 변경이 필요하면 그 부분만 질의한다. 기존 명세를 갱신할 때는 Feature ID·합의·진행 근거를 유지하며, 재구성을 요청받으면 이전 항목과 새 묶음의 대응을 남긴다.

## 담당자 질의 작성

- **Q번호 하나에는 결정 하나만 담는다.** 최대 5개 제한을 맞추려고 여러 결정을 한 문장에 묶지 않는다. 한 번에 질문 하나만 하라는 뜻은 아니며 독립된 질문을 최대 5개까지 함께 제시할 수 있다.
- 질문 본문은 사용자가 답할 한 가지 선택이나 값을 분명히 묻는다. 배경, 예시, 추천 이유는 질문 문장에 이어 붙이지 않고 별도 줄에 쓴다. 도메인을 모르는 사람도 이해할 말로 설명하고, 답변에 따라 달라지는 결과는 선택지나 짧은 사례로 보여 준다.
- 같은 맥락을 함께 보여 줘야 하면 공통 주제 아래 `Q2-1`, `Q2-2`처럼 나눈다. 각 하위 질문에도 한 가지 결정, 답변 자리, 상태를 따로 두고 최대 5개를 셀 때 각각 한 개로 센다. 기존 번호를 유지해야 하면 질문을 지우거나 다시 번호 매기지 말고 하위 번호로 연결한다.
- **긴 표보다 질문별 블록을 기본으로 한다.** 템플릿에 따라 질문·선택지·추천과 이유·답변·상태·관련 Feature를 줄바꿈해 보여 준다. 전체 현황 표가 필요하면 번호·주제·상태 정도만 요약하고 실제 질문과 답변 기록을 여러 열에 압축하지 않는다.
- 선택지는 가능한 경우 A/B 등으로 구분하고, 각 선택지가 실제로 어떤 의미인지 적는다. 숫자를 묻는 경우 단위와 답변 예시를 붙인다. 사용자가 `Q1: A`, `Q2: 15분`처럼 답할 수 있게 하되 자유로운 설명도 허용한다.
- 추천안은 선택한 경우 적용될 내용이 처음부터 명확해야 한다. 배수·비율 표현은 비교하는 두 값과 단위를 풀어 쓴다. 추천 이유는 따로 설명하고 추천안과 실제 합의를 구분한다.
- 질문을 보내기 전에 사용자가 각 질문에 선택지 하나나 값 하나로 답했을 때 필요한 결정이 끝나는지 확인한다. 답변 뒤에 다시 물어야 할 독립적인 필수 결정이 숨어 있으면 처음부터 분리해 우선순위에 포함한다.

## 답변 반영과 추가 질문

- 답변은 먼저 확정된 결정부터 Feature·통과 조건·질의 상태에 반영하고 실제 원문과 출처를 보존하거나 대화 기록으로 연결한다. 사용자가 표현을 달리했더라도 명확히 답한 내용을 다시 묻지 않는다. 일부 답변을 묶음 전체의 합의로 확대하지 않는다.
- 답변 기록은 현재 적용할 정책과 남은 판단을 먼저 읽을 수 있게 정리한다. 긴 원문이나 최초 추천안은 별도 기록으로 보존하고, 이미 끝난 질문을 미응답 질문 사이에 반복해서 길게 보여 주지 않는다. 상태는 `미응답·일부 답변·답변 완료·위임`을 구분한다.
- **추가 질문은 필요한 결정이 실제로 남았을 때만 한다.** 원문·이전 답변과의 충돌이나 결과·범위·통과 조건이 달라지는 모호함이 있는지 먼저 확인한다. 결과에 영향 없는 기술 선택이나 사용자가 요구하지 않은 추가 최적화·세부 가중치는 자율 판단 또는 제안 메모로 남기며 자동으로 새 질문이나 보류 사유로 만들지 않는다.
- 추가 질문이 필요하면 `이미 정해진 내용`, `아직 필요한 답변`, `이 답변이 필요한 이유`를 먼저 짧게 구분하고 남은 한 가지 결정만 묻는다. 앞선 질문에 여러 결정을 섞어 생긴 누락이면 새 요구사항인 것처럼 제시하지 말고 그 점을 밝힌다.
- 선호와 강제 조건을 구분한다. 답변이나 위임 없이 선호를 강제 한도로 바꾸지 않으며, 실제로 필요한 선호 간 우선순위를 묻더라도 이미 답한 개별 선호를 재질문하지 않는다.
- 위임된 선택에는 범위·선택·이유·영향을 적는다. 결과에 영향 없는 기술 선택은 자율적으로 정하고 같은 내용을 업무 승인 질문으로 돌리지 않는다.

## 필수 기준

- 도메인을 모르는 독자가 명세만 읽고 Feature의 통과·실패를 판정할 수 있다.
- 원문 필수 요구사항을 빼지 않는다.
- 없는 데이터·담당자 답변을 만들지 않는다.
- 미구현이나 필수 검증의 실패·미검증을 완료로 표시하지 않는다.
- 명세만 요청받았으면 코드를 바꾸지 않는다.
